# Dominion Adaptive Revenue Core

**Governance:** RADAH MEMSHALAH  
**System doctrine:** ONE SYSTEM · ONE BRAIN · MANY LANES  
**Status:** production-candidate control-plane contract; runtime proof still required.

## Purpose

Dominion uses one shared intelligence and governance loop across commerce, YouTube, SEO, affiliate, publishing, B2B, SaaS, services, Amazon, social, and future lanes. Lane-specific agents are sensors/executors, not independent brains.

## Canonical loop

SENSE → VERIFY → SCORE → DECIDE → EXECUTE WITHIN AUTHORITY → ATTRIBUTE → LEARN → GOVERN → REALLOCATE.

Every material asset has a living feasibility score. The score is evidence, not authority. A sufficiently evidenced lower-threshold breach escalates to Council rather than causing automatic destruction. A sufficiently evidenced upper-threshold breach creates a scale candidate rather than automatic spend.

Council dispositions are SCALE, HOLD, REPAIR, PIVOT, HARVEST, RETIRE.

## Noise protection

Lifecycle changes require minimum confidence and sample size. Production policy should additionally require persistent breach windows appropriate to each lane. One bad observation must not kill a viable asset.

## Decision memory

Every material decision records WHAT, WHY, EVIDENCE, ACTION, RESULT, and LESSON. Decision receipts are timestamped and hash-addressed. First-party outcomes outrank external estimates for claims about Dominion economics.

## Obsidian role

Obsidian is the human-readable operating memory and command surface, not a second brain. It should render asset state, score history, evidence, Council cases, decisions, attribution, incidents, and lessons sourced from canonical machine records.

## Revenue focus after core closure

After this shared spine is accepted, engineering priority moves to qualified traffic and attributable revenue experiments. New lane features should be rejected unless they improve sensing, conversion, attribution, learning, governance, reliability, or proven revenue capacity.

## Acceptance gates

1. Deterministic scoring tests pass.
2. Low-confidence/noisy observations cannot trigger Council lifecycle action.
3. Persistent lower-threshold degradation produces a Council case.
4. Scale candidates require governed review before material resource expansion.
5. Decision receipts reject unknown dispositions and carry SHA-256 identity.
6. No lifecycle module performs publishing, spend, customer contact, money movement, destructive mutation, or credential changes.
7. Runtime integration emits evidence before production status is claimed.

## Stamp

This document defines the canonical adaptive asset-lifecycle doctrine for Dominion. A repository commit proves code provenance; it does not by itself prove production runtime behavior or revenue.
